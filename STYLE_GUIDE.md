## Observed founder writing pattern

The raw voice tends to:

- begin with a question, possibility, constraint, or unfinished thought;
- use short fragments, arrows, numbered items, and labels;
- move quickly between problem, technology, economics, customers, and execution;
- connect apparently separate questions into one system;
- ask what can be free, local, reusable, automated, or connected;
- think in flows: input → processing → output;
- use diagrams and spatial relationships as part of the thinking;
- leave uncertainty visible instead of hiding it;
- return to the same question from a new angle until a system emerges.

## Technical voice

The cleaned-up technical voice is systems-first and implementation-heavy. It tends to:

- state the objective directly;
- define constraints before proposing solutions;
- use concrete architecture and file structures;
- prefer practical instructions over broad motivational language;
- separate phases, responsibilities, and interfaces;
- use short declarative sentences for important rules;
- explain why a design choice exists;
- treat simplicity and reuse as engineering constraints.

The MW.AI repository is a clear example: it opens with a precise product definition, then moves through vision, stack, architecture, setup, workflow, contribution rules, and roadmap. fileciteturn11file0L2-L2

## Newsletter transformation

Do not turn the raw material into generic polished prose.

Use this transformation:

RAW QUESTION
→ preserve the original tension
→ identify the actual problem
→ connect the scattered ideas
→ show the system that emerges
→ show what changed
→ end with the next unanswered question

A useful issue can therefore contain:

**QUESTION** — what started the thought.

**RAW** — the original fragment, sketch, or constraint.

**SYSTEM** — how the pieces connect.

**BUILD** — what was actually implemented or tested.

**LESSON** — what changed in the thinking.

**NEXT** — what remains unanswered.

## Avoid

- generic AI hype;
- fake certainty;
- excessive motivational language;
- long introductions before the useful point;
- pretending a prototype is a production system;
- turning every note into a polished success story;
- removing the strange jumps that reveal how the idea developed.

## Founder Story rule

Founder Story pieces should sound like a record, not a biography written after the fact.

Keep the chronology, constraints, questions, failures, decisions, and changes visible.

Do not invent motives or events that are not present in the source material.

## Editorial goal

The newspaper should feel like a serious publication built from a founder's actual working notebook: technical, questioning, experimental, slightly unfinished, and progressively more structured as the ideas become systems.
